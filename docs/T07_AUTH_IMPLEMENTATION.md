# 과제7 인증·계정 격리 구현 설명 (검증 상태 구분)

> 기준: `assignment-7` 브랜치, 2026-10-28. 구현 사실과 실제 실행 검증 결과는 구분한다. `main`에 배포된 과제6은 변경하지 않았다.

## 1. 무엇을 구현했는가
과제6의 공개 Plan → Do → See 흐름을 유지하면서 과제7 브랜치에 계정 인증 경계를 추가했다. 첫 화면(`/`)은 로그인/회원가입, 로그인 후 `/diary`는 기존 다이어리, `/account`는 계정 설정이다. 계획과 그 하위 할 일·실행·회고·수정 이력은 로그인 사용자별로 조회·수정·내보내기를 분리한다. 로그인되지 않은 사용자의 데이터 API 요청에는 401을 반환한다.

## 2. 어떻게 구현했는가
- 회원가입: 이메일은 소문자·공백 제거 후 중복을 검사한다. 비밀번호는 12자 이상으로 제한하고 Node `crypto.scrypt`로 고유한 16바이트 난수 salt를 포함한 해시만 저장한다.
- 로그인: DB 해시 검증 뒤 32바이트 난수 토큰을 생성한다. 원본 토큰은 `HttpOnly`, `SameSite=Strict` 쿠키로 전달하며 DB에는 SHA-256 해시만 저장한다.
- 세션: 7일 만료, 로그아웃 시 서버의 세션을 폐기한다. 비밀번호 변경 시 사용자에 속한 이전 세션을 모두 무효화한다.
- 데이터 소유권: `plans.owner_user_id`를 기준으로 하위 테이블을 FK 조인한다. 사용자 ID는 요청 본문·URL·헤더가 아니라 `requireAuth`가 확인한 세션에서 가져온다.
- 상태 변경: `Origin`을 검사해 다른 출처 요청을 막는다. 인증 오류는 401, 허용하지 않는 출처는 403, 다른 소유자의 개별 계획/기록은 404를 반환하도록 설계했다.
- 이전 데이터: 과제6 기존 행은 `owner_user_id=NULL`로 유지한다. 새 계정에 자동 귀속시키지 않으며, 승인된 별도 이전 전까지 로그인 사용자 화면에 노출하지 않는다.

## 3. 이 방식을 선택한 이유
해시+개별 salt는 비밀번호 원문 저장을 막고 같은 비밀번호를 설정한 사용자도 서로 다른 저장값을 갖도록 한다. 서버 세션은 로그아웃·비밀번호 변경 시 즉시 폐기할 수 있다. `HttpOnly` 쿠키는 JS 코드가 토큰을 직접 읽지 못하게 한다. DB 조회 조건에 소유권을 포함시키면 사용자가 임의의 데이터 ID를 전송해도 다른 계정의 데이터를 조회·변경할 수 없게 한다. 과제6의 미인증 레코드를 자동 귀속하지 않는 이유는 기존 공개 데이터의 소유자를 안전하게 추정할 수 없기 때문이다.
