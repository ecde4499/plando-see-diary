# T07 기존 데이터 계정 이전 — 폐기형 DB 리허설 결과 판정 기준

## 범위
과제6에서 만들어진 로그인 없는 기존 계획 및 그 하위 기록을, 확인된 계정으로 이전할 수 있는지 검증하기 위한 **코드 및 절차**다. 이번 단계에서는 운영 Supabase 또는 Render를 수정하지 않았다.

## 기본 안전 정책
- 계정 소유자 이전 기능은 `tools/t07-legacy-transfer.cjs`에 **내부 함수**로만 존재한다. 외부에서 호출하는 HTTP API 또는 일반 사용자 실행 명령은 없다.
- `previewOrRehearseTransfer(pool, { targetUserId, planIds })`의 기본값은 **읽기 전용 미리보기**다. 이름이 완전히 일치하는 계획 UUID를 지정해야 하며, 모든 계획 자동 귀속은 지원하지 않는다.
- 실제 소유자 변경 옵션은 `NODE_ENV=test`, `approval='DISPOSABLE_DB_ONLY'`, 이름에 `test`가 포함된 DB라는 조건에서만 허용한다.
- 운영 DB용 적용 절차는 **의도적으로 구현하지 않았다.** 백업과 원 소유권 확인, 운영 이전에 대한 명시적 승인이 필요하다.

## 리허설 검증
`.github/workflows/t07-verify.yml`의 `isolated-postgres-http` 작업은 실행 시마다 생성하는 별도 PostgreSQL DB에서 다음을 검사하도록 구성됐다.

1. 인증 스키마가 추가되기 전에 과제6 형식의 원본 계획/할 일/실행 기록을 저장한다.
2. 인증 스키마 추가 이후에도 원본 계획의 소유자 `NULL` 상태와 하위 기록이 보존되는지 확인한다.
3. A/B 계정을 만들었을 때 자동 귀속이 이루어지지 않는지 확인한다.
4. 이전 대상으로 지정된 계획 ID만 **읽기 전용 미리보기** 후, 폐기형 테스트 DB에서만 A에게 귀속시키는 리허설을 실행한다.
5. 계획·할 일·실행 기록의 **원래 ID를 유지**하고, 원본 테이블 여섯 개의 전체 건수가 이전 전후 변하지 않는지 확인한다.
6. 이전 후 A는 본인 기록을 조회할 수 있고 B는 조회할 수 없는지 확인한다.
7. 같은 계획을 B에게 재귀속하려는 시도가 실패하는지 확인한다.
8. 계획과 연결된 회고가 선택 밖의 계획을 참조하거나, 선택 밖의 계획이 선택한 계획을 참조하면 이전을 거부한다.
9. B의 계정을 삭제해도 A의 기존 계획과 이전한 계획이 유지되는지 확인한다.

**모든 검증이 실제 성공했는지는 최신 GitHub Actions의 실행 결과로 확인해야 한다.** 테스트 코드를 작성했다는 사실만으로 통과했다고 기록하지 않는다.

## 운영 이전을 진행하기 전 필수 확인
- 운영 DB 백업 및 별도 DB 복원 리허설 완료
- 기존 데이터가 실제로 누구의 것인지 확인
- 이전할 계획 UUID 목록을 관리자가 확인
- 연결된 회고·다음 계획 관계까지 함께 검토
- 이전 전후 여섯 테이블의 건수와 주요 연결 관계 재검증
- 이전 후 각 계정으로 조회·수정·삭제·내보내기 교차 검증
- 사용자에게 이전/배포에 대해 명시적으로 승인을 받은 뒤에만 운영 작업 착수

## 이번 리허설에 포함되지 않은 것
- 운영 Supabase 백업이나 복원
- 실제 사용자 계정 선택 및 운영 데이터 귀속
- 운영 Render 서비스의 과제7 업데이트
- 실제 사용자의 5일 데이터 작성 및 전후 지표 비교

진행 상태: **리허설 코드와 테스트 추가, 새 CI 결과 미확인**.
