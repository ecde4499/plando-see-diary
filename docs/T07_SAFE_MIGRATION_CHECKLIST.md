# 과제7 — 운영 데이터 이전 전 사전 점검 (읽기 전용)

## 목적
과제6에 로그인 없이 저장한 기존 기록이 과제7 도입 과정에서 누락·잘못 귀속·삭제되지 않도록 **현재 데이터의 건수와 인증 스키마 유무만 확인**한다. 이 단계는 데이터 이전이 아니다.

## 현재 구현
`tools/t07-preflight.cjs` (`npm run preflight:t07`)는 읽기 전용 PostgreSQL 트랜잭션(`BEGIN READ ONLY`)에서 다음 사항을 집계한다.

- 원본 6개 테이블(`plans`, `plan_revisions`, `tasks`, `execution_logs`, `completion_events`, `reflections`) 건수
- 인증 테이블(`app_users`, `auth_sessions`) 존재 여부와 건수
- `plans.owner_user_id` 열 유무
- 소유자 지정 완료 계획 수 및 기존 미귀속(`NULL`) 계획 수
- 실행 시각(UTC), `READ_ONLY` 확인 표기

**비밀번호, 이메일, 세션 쿠키, 연결 주소, 작업 본문은 결과에 출력하지 않는다.**

## 언제 실행하나?
1. 별도 PostgreSQL 테스트 DB에서 검증이 통과한 다음.
2. 과제6 운영 Supabase 데이터의 **백업/복원 방법을 점검**한 다음.
3. 운영 DB를 점검할 필요가 있고, 사용자가 명시적으로 승인한 다음. 코드는 읽기 전용이지만 운영 DB 자격 증명이 필요하므로 점검할 때만 실행한다.

```bash
git switch assignment-7
git pull origin assignment-7
npm ci
# 실제 DB 접속 정보가 올바르게 로컬 환경변수로 주어진 환경에서만 실행
npm run preflight:t07
```

`.env` 파일 또는 연결 문자열을 스크린샷이나 대화에 붙여넣지 않는다.

## 실제 운영 이전에서 금지된 일
- 계정을 새로 만들었다는 이유로 `owner_user_id=NULL`인 과제6 기록을 자동으로 자기 계정 소유로 바꾸지 않는다.
- 로그인하지 않은 사용자가 제출한 user_id/owner_user_id를 근거로 데이터 이전을 하지 않는다.
- 백업과 운영 적용 승인 없이 `007_auth_foundation.sql`을 운영 DB에서 실행하지 않는다.
- 검증 전 `assignment-7` 브랜치를 Render 운영 서비스에 배포하지 않는다.

## 나중에 별도 승인받아 진행할 순서
1. **운영 DB 백업 + 복구 리허설** 및 현재 원본 건수 보존.
2. 인증 스키마 운영 적용 계획 검토. 실제 적용 대상 DB와 시각을 확인.
3. 과제6 기존 계획의 원 소유자 확인. 공용·제3자 기록 여부 확인.
4. 본인 계정을 별도로 생성한 다음 관리자 승인하에 **확인된 계획 ID만** 이전. 관련 `source_reflection_id` / `next_plan_id` 등 계획 간 관계도 확인.
5. 이전 전후 계획/할 일/실행/완료/수정 이력/회고 건수 대조.
6. A/B 다른 계정 접근 401/404 재검증, 로그아웃/비밀번호 변경 재검증, JSON 내보내기 범위 확인.
7. 승인 후에만 Render 배포 및 최종 검증.
